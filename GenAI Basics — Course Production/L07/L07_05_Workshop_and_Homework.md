## 1. Цель и суть домашнего задания

Цель этого задания — **перевести использование AI-ассистентов из интуитивного чата в строгую инженерную плоскость**. 

Каждый день разработчики и инженеры сталкиваются с десятками рутинных задач: написание тестов, рефакторинг методов, составление релиз-ноутсов, ответы саппорту, проверка конфигов. Задача студента — спроектировать **Copilot Operating Map (Операционную карту Copilot)**, в которой четко разграничены зоны ответственности, источники правды и точки верификации человеком.

## 2. Формат и структура сдаваемого файла (`copilot_operating_map.md`)

Студент создает в своем репозитории файл `genai-homeworks/L07/copilot_operating_map.md`, содержащий две обязательные секции:

### Секция 1: Матрица задач (Copilot Operating Map Matrix)
Необходимо выбрать **3 реальные задачи** из своей повседневной практики (или взять эталонный сценарий курьерской доставки Glovo / Project Northstar) и заполнить таблицу:

| Поле матрицы | Требование к содержанию | Пример заполнения (Эталон Glovo Courier) |
| :--- | :--- | :--- |
| **1. Задача (Task)** | Конкретный атомарный процесс (не «написать код», а конкретное действие) | Добавление ночного повышающего коэффициента в калькулятор тарифов курьера |
| **2. Поверхность (Surface)** | Точное семейство и режим инструмента | GitHub Copilot в VS Code (Agent Mode / Copilot Edits) |
| **3. Источник контекста (Context Source)** | Где физически живет правда задачи | Файл тикета Jira `GLV-402`, файл тарифов `pricing.py`, файл тестов `test_pricing.py` |
| **4. Разрешенное действие (Allowed Action)** | Что разрешено делать ассистенту | Предложить план, отредактировать локальные файлы и запустить unit-тесты в терминале |
| **5. Контрольная точка человека (Human Checkpoint)** | Что именно обязан проверить инженер перед принятием | Построчный просмотр diff в `pricing.py` (проверка отсутствия деления на ноль) + зеленый pytest |
| **6. Сохраняемый артефакт (Evidence)** | Доказательство качественного выполнения | Pull Request с прикрепленным логом прохождения тестов CI |
| **7. Риск / Политика (Policy Dependency)** | Что может заблокировать задачу или нарушить безопасность | Запрет на использование сторонних непроверенных MCP-серверов в корпоративной IDE |

### Секция 2: Эталонный 4-компонентный промпт (Microsoft Learn Standard)
Для одной из трех описанных задач напишите эталонный рабочий промпт, строго разбитый на 4 официальных ингредиента:
* `[Goal]`: Четкий глагол действия и формулировка целевого результата;
* `[Context]`: Бизнес-обоснование задачи, целевая аудитория и этап жизненного цикла;
* `[Source]`: Явная ссылка на авторитетный файл, ссылку или стенограмму;
* `[Expectations]`: Ограничения по длине, стилю, структуре и обязательное цитирование первоисточников.

## 3. Эталонный бенчмарк для калибровки (Glovo Food Delivery Courier)

Если вы не можете использовать данные своего закрытого корпоративного проекта, используйте сквозной бенчмарк курса — **Сервис курьерской доставки Glovo**:
* **Задача А (Software Delivery):** Реализация логики доплаты курьеру за доставку в ливень в репозитории микросервиса диспетчеризации (GitHub Copilot Agent Mode). Чекпоинт: покрытие тестами 100%, проверка пограничных условий (0 км, отрицательная сумма).
* **Задача Б (Knowledge Work):** Подготовка памятки для курьеров по правилам безопасности в плохую погоду на основе регламента службы логистики (Microsoft 365 Copilot в Word). Чекпоинт: факт-чекинг пунктов регламента, отсутствие выдуманных компенсаций.
* **Задача В (Local Preflight):** Проверка готовности рабочего места оператора колл-центра перед началом смены (локальный чек-лист на Windows). Чекпоинт: валидация доступов к телефонии и CRM.

## 4. Критерии оценки (100-балльная шкала)

| Критерий | Баллы | Что оценивается |
| :--- | :---: | :--- |
| **1. Корректность выбора поверхностей** | 25 | Поверхности выбраны строго по источнику правды (код ➔ GitHub, документы ➔ M365). Нет путаницы логотипов. |
| **2. Границы действий и Blast Radius** | 25 | Отсутствие иллюзий полной автономии. Запрет на автоматические финансовые действия и деплой без CI. |
| **3. Четкость контрольных точек (Human Checkpoints)** | 25 | Названы конкретные действия инженера: инспекция diff, запуск pytest, сверка цитат (не абстрактное «посмотрю глазами»). |
| **4. Эталонный 4-компонентный промпт** | 25 | Промпт безупречно структурирован по блокам Goal, Context, Source, Expectations. Наличие жестких ограничений. |
