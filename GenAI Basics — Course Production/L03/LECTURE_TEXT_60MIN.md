## Блок 2: Настройка клиента, гигиена секретов, дедлайны и ретраи (08:00 – 18:00)

### 2.1. Ментальная модель SDK
**Слова лектора:**
«Давайте зафиксируем базовую ментальную модель. Что такое Python SDK провайдера (OpenAI, Anthropic или Google)? 
Библиотека Python **не содержит внутри себя модель**. Веса модели не загружаются в память вашего сервера. SDK — это просто специализированный HTTP-клиент, который:
1. Сериализует ваш вызов в JSON-запрос по HTTPS.
2. Проставляет заголовки аутентификации.
3. Отправляет байты в облачный кластер инференса.
4. Десериализует входящие HTTP-ответы или поток Server-Sent Events в типизированные объекты языка Python.

Поэтому первый навык инженера при работе с LLM — это не «промпт-инжиниринг», а **сетевая гигиена и безопасность секретов**».

### 2.2. Правило «Нулевой утечки» и конфигурация окружения
**Слова лектора:**
«Запомните правило: API-ключ в коде — это скомпрометированный ключ. Ключ, случайно попавший на скриншот во время зум-колла или закоммиченный в GitHub — это уязвимость и потенциальный счет на тысячи долларов за считанные часы.

Мы соблюдаем три жестких стандарта:
1. `.env` **всегда** находится в `.gitignore`. В репозиторий попадает исключительно `.env.example` с фиктивными плейсхолдерами.
2. Имя модели **никогда не зашивается хардкодом в логику**. Модель — это конфигурационный параметр среды (`OPENAI_MODEL=gpt-4o` или `gemini-2.0-flash`). Завтра провайдер обновит модель или снимет старый снапшот с деплоя — ваш код не должен требовать переписывания.
3. Локальный preflight-чек: перед тем как отправлять платный сетевой запрос, приложение локально проверяет наличие переменных окружения и соответствие версий библиотек».

### 2.3. Инициализация клиента: Дедлайны и лимиты повторов
**Слова лектора:**
«Посмотрим на каноническую инициализацию клиента:

```python
from openai import OpenAI
import os

client = OpenAI(
    api_key=os.environ["OPENAI_API_KEY"],
    timeout=20.0,       # Жесткий дедлайн сетевого сокета
    max_retries=2       # Ограниченный бюджет повторных попыток
)
```

Обратите внимание на два параметра, которые новички обычно опускают:
- `timeout=20.0`: если удаленный кластер завис под пиковой нагрузкой, ваш рабочий процесс не должен висеть бесконечно, блокируя потоки пула серверов. 20 секунд — это дедлайн.
- `max_retries=2`: если сеть моргнула или провайдер ответил ошибкой `503 Service Unavailable`, SDK автоматически повторит запрос с экспоненциальной задержкой. Но мы ограничиваем это число, чтобы не сжечь бюджет и не заблокировать очередь».

## Блок 3: Архитектура стриминга: SSE и физика задержек (18:00 – 30:00)

### 3.1. Почему блокирующий вызов убивает пользовательский опыт
**Слова лектора:**
«Давайте разберем физику задержек. Когда мы делаем обычный вызов `stream=False`, клиент отправляет HTTP POST запрос и сокет замирает в ожидании. 
Модель генерирует ответ авторегрессионно: токен за токеном. Если ответ составляет 600 токенов, а скорость генерации — 30 токенов в секунду, сервер будет молчать **20 секунд**. Все это время пользователь видит белый экран или застывший спиннер. 

Для человека ожидание более 1.5–2 секунд ощущается как «система зависла». Кроме того, если на 19-й секунде оборвется Wi-Fi или упадет балансировщик, клиент потеряет 100% сгенерированного ответа, а вы заплатите за токены, которые никто не увидел».

### 3.2. Механика Server-Sent Events (SSE)
**Слова лектора:**
«Стриминг (`stream=True`) меняет транспортный протокол на **Server-Sent Events (SSE)**.
Соединение HTTP открывается и не закрывается сразу. Заголовок ответа содержит `Content-Type: text/event-stream`.
Как только ускоритель (GPU/TPU) вычисляет очередной токен или фрагмент (chunk), он немедленно отправляет его в открытый сокет в виде текстового фрейма:
`data: {"choices": [{"delta": {"content": "Привет"}}]}`

Посмотрим на архитектурную схему (Слайд 9 / Схема streaming_architecture.svg):
- **Time To First Token (TTFT):** Задержка до первого видимого токена составляет от 200 до 350 миллисекунд! Пользователь мгновенно видит начало печати. Для него приложение ощущается молниеносным, хотя суммарное время генерации осталось тем же.
- **Inter-Token Latency (ITL):** Задержка между последующими токенами (обычно 15–30 мс на современных моделях).

Давайте взглянем на код обработки стрима:

```python
response = client.chat.completions.create(
    model=os.environ.get("OPENAI_MODEL", "gpt-4o"),
    messages=[{"role": "user", "content": "Опиши шаги настройки CI/CD"}],
    stream=True,
    stream_options={"include_usage": True} # Обязательно: запрос финальной статистики токенов
)

for chunk in response:
    if chunk.choices and chunk.choices[0].delta.content:
        token = chunk.choices[0].delta.content
        print(token, end="", flush=True)
    
    # Финальный чанк передает статистику использования токенов
    if chunk.usage:
        print(f"\n[Метрики] Использовано токенов: {chunk.usage.total_tokens}")
```

**Инженерное предостережение:**
Стриминг — это интерфейс для *человека*. Если ваш потребитель — другая программа (микросервис базы данных или платежный шлюз), ей не нужны частичные дельты. Ей нужен готовый валидный объект. Не путайте стриминг для UI со структурированным контрактом для API».

## Блок 4: Структурированный вывод: от промпта к Constrained Decoding (30:00 – 44:00)

### 4.1. Три поколения структурирования: почему «Верни JSON» больше не используется
**Слова лектора:**
«Переходим к главному блюду сегодняшней лекции — Structured Outputs.
Исторически разработчики прошли три этапа:

1. **Уровень 1: Промптинг («Пожалуйста, верни только JSON»).**
   Мы писали: *«Ответь в формате JSON с ключами category и priority»*.
   Что получали на практике? Модель оборачивала ответ в тройные бектики: ` ```json ... ``` `, добавляла вежливое: *«Вот ваш JSON:»* или случайно пропускала запятую. Нагрузочный тест показывал: от 5% до 15% запросов падали с `json.decoder.JSONDecodeError`. В продакшене это катастрофа.

2. **Уровень 2: Retry Loops (Повтор при ошибке валидации).**
   Мы ловили ошибку через Pydantic, писали модели: *«Ты ошиблась в JSON, вот стек ошибки, попробуй снова»*.
   Это работало, но утроило среднюю задержку и затраты на токены.

3. **Уровень 3: Constrained Decoding (Принудительное декодирование грамматик).**
   Это технологический прорыв конца 2024 года, который теперь доступен во всех основных API (OpenAI Structured Outputs `strict=True`, Anthropic Tool Calling, Gemini `response_schema`).

Как это работает на уровне физики модели? (Слайд 13 / Схема structured_output_boundary.svg).
Ваша Pydantic-схема преобразуется в детерминированный автомат — **контекстно-свободную грамматику (CFG)**.
Когда нейросеть выбирает следующий токен из словаря в 128 000 слов, система маскирования проверяет: какие токены допустимы грамматикой прямо сейчас?
Если открыта фигурная скобка `{`, допустим только токен имени поля в кавычках. Символ буквы или недопустимый символ просто маскируется (его лоджит приравнивается к минус бесконечности).
**Следствие:** Модель физически не способна сгенерировать невалидный JSON. Вероятность синтаксической ошибки равна строго **0.00%**».

### 4.2. Канонический Pydantic-контракт
**Слова лектора:**
«Давайте напишем контракт на Pydantic:

```python
from pydantic import BaseModel, Field
from typing import Literal

class TicketTriage(BaseModel):
    category: Literal["bug", "billing", "feature_request", "inquiry"]
    priority: Literal["low", "medium", "high", "urgent"]
    summary: str = Field(description="Краткая суть проблемы в одно предложение")
    customer_sentiment: int = Field(ge=1, le=10, description="Оценка от 1 (ярость) до 10 (восторг)")
    needs_human_review: bool = Field(description="Флаг необходимости ручной проверки модератором")
```

Посмотрите на метод `client.beta.chat.completions.parse`:

```python
completion = client.beta.chat.completions.parse(
    model="gpt-4o",
    messages=[
        {"role": "system", "content": "Ты — сервисный шлюз триажа. Классифицируй обращение."},
        {"role": "user", "content": "После ввода промокода корзина зависает и выдает ошибку 500."}
    ],
    response_format=TicketTriage,
)

ticket: TicketTriage = completion.choices[0].message.parsed
print(f"Категория: {ticket.category}, Приоритет: {ticket.priority}")
```

В переменную `ticket` попадает не строка, не словарь, а **настоящий типизированный экземпляр класса `TicketTriage`**. IDE подсвечивает поля, автодополнение работает, а валидация типов уже выполнена».

### 4.3. Три уровня валидации
**Слова лектора:**
«Внимание! Запишите это правило, это частая ошибка на собеседованиях:
- **Уровень 1: Синтаксическая валидность (Schema Validity).** Формат JSON корректен, типы совпадают. Это гарантирует Constrained Decoding.
- **Уровень 2: Семантическая валидность (Semantic Validity).** Поняла ли модель контекст? Не перепутала ли она причину и следствие?
- **Уровень 3: Бизнес-валидность (Business / Action Validity).** Существует ли указанный ID клиента в базе данных? Разрешен ли возврат средств по регламенту для этой страны?

Схема защищает нас от падения программы (Level 1). Но валидацию бизнес-правил (Level 3) мы обязаны делать детерминированным Python-кодом **после** вызова модели!».

## Блок 5: Обработка неопределенности, сбоев и наблюдаемость (44:00 – 52:00)

### 5.1. Паттерн «Клапан неопределенности» (Ambiguity Escape Hatch)
**Слова лектора:**
«Что происходит, когда пользователь присылает бессмысленный текст, например: *«Ыыыы, ничего не работает, почините быстро!»*?
Если в вашей схеме есть только категории `["bug", "billing"]`, модель будет вынуждена гадать. Она ткнет пальцем в небо с уверенным видом.

В enterprise-системах мы обязаны проектировать **путь безопасного отступления**:
1. Явный флаг `needs_human_review: bool`.
2. Значение `category: Literal[..., "unclear"]`.
3. Поле `confidence_score: float = Field(ge=0.0, le=1.0)`.

Если уверенность модели ниже порога (например, < 0.75), тикет не отправляется в автоматический биллинг. Он маршрутизируется в очередь живого оператора. Это сохраняет доверие к системе».

### 5.2. Конверт наблюдаемости (The Observability Envelope)
**Слова лектора:**
«Ни один вызов в продакшене не должен быть анонимным. Мы оборачиваем каждый результат в конверт телеметрии:
- `request_id`: уникальный идентификатор вызова от провайдера (по нему саппорт OpenAI или Azure может найти сбой).
- `latency_ms`: общее время исполнения.
- `ttft_ms`: время до первого токена (при стриминге).
- `prompt_tokens` и `completion_tokens`: точный расход токенов.
- `timestamp`: метка времени в UTC.

Без этого конверта невозможно оптимизировать затраты и расследовать инциденты».
